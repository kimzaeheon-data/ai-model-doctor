# 변경 계획 및 승인 게이트 v0.1 설계

## 목적

진단 결과를 실제 설정 변경과 분리하고, 사용자가 변경 전후 값·근거·위험·비용을 검토한 뒤 명시적으로 승인한 항목만 다음 실행 단계에 전달한다.

M4는 설정 파일을 수정하거나 학습을 실행하지 않는다. 실제 후보 설정 생성과 재학습은 M5의 책임이다.

## 처리 흐름

```text
evaluation.json + diagnosis.json
              ↓
       change-plan.json
              ↓
       사용자 검토 및 결정
              ↓
         approval.json
              ↓
   승인 게이트가 계획·승인 검증
              ↓
      승인된 변경 목록만 반환
```

## 변경 계획의 불변성

- 변경 계획은 생성 후 내용을 수정하지 않는다.
- 사용자가 수정 요청을 하면 기존 계획을 덮어쓰지 않고 새로운 `plan_id`로 다시 생성한다.
- 승인 기록에는 변경 계획 전체의 SHA-256 digest를 저장한다.
- 승인 후 계획 내용이 바뀌면 digest가 달라지므로 승인 게이트가 거부한다.

## 허용 범위

허용 설정과 값 범위의 단일 기준은 `configs/change-policy.yaml`이다.

- 학습: learning rate, batch size, epochs, imgsz, optimizer, weight decay, patience, augmentation
- 추론: confidence, IoU
- 대상 파일: `candidate/args.yaml`, `candidate/inference.yaml`

소스 코드, 데이터셋, 라벨, 모델 구조, 체크포인트, 원본 run 파일 및 배포 설정은 변경할 수 없다.

## 계획 생성 조건

- `warning` 상태인 진단을 하나 이상 근거로 연결해야 한다.
- `pass` 또는 `insufficient_data`만 존재하면 설정 변경 계획을 만들지 않는다.
- 각 변경은 현재 값과 제안 값이 달라야 한다.
- 제안 값은 정책에 정의된 타입, 범위 및 enum을 만족해야 한다.
- 각 변경에는 사람이 읽을 수 있는 diff, 예상 효과, 위험 및 실행 비용을 포함한다.

## 사용자 결정

| 결정 | 의미 | 승인된 변경 |
| --- | --- | --- |
| `approve_all` | 전체 승인 | 계획의 모든 `change_id` |
| `approve_selected` | 일부 승인 | 사용자가 고른 `change_id`만 |
| `request_revision` | 수정 요청 | 없음 |
| `cancel` | 계획 취소 | 없음 |

`request_revision`에는 한 개 이상의 수정 요청 문장이 필요하다. `cancel`과 수정 요청 상태에서는 실행 권한이 생성되지 않는다.

## 승인 게이트

승인 게이트는 다음을 모두 확인한다.

1. 계획과 승인 JSON이 각 스키마를 만족한다.
2. `plan_id`와 `plan_digest`가 일치한다.
3. 계획의 모든 변경이 현재 허용 정책 안에 있다.
4. 승인된 `change_id`가 계획에 실제로 존재한다.
5. 승인 결정과 승인 범위가 서로 모순되지 않는다.

검증이 성공해도 M4는 승인된 변경 객체를 반환할 뿐 파일을 수정하지 않는다.

## 완료 기준

- 승인되지 않은 변경 목록은 게이트를 통과하지 못한다.
- 각 변경에 사람이 읽을 수 있는 diff가 있다.
- 허용되지 않은 설정이나 대상 파일은 차단된다.
- 계획 변조 시 기존 승인 기록은 무효가 된다.
- 전체 승인, 일부 승인, 수정 요청 및 취소를 구분할 수 있다.
